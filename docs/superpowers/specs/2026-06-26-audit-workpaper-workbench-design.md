# 审计底稿工作台前端优化设计

## 目标

- 将当前偏通用聊天式的前端，优化为更适合审计底稿审阅的专业工作台。
- 强化 `输入`、`证据`、`结果`、`状态` 四类信息的分层，提升阅读效率与可信感。
- 在尽量复用现有 `Next.js + Tailwind + 组件库` 基础上，完成页面结构与交互层升级，而不是推倒重做。
- 修复当前页面中与 Web Interface Guidelines 不一致的关键问题，尤其是可访问性、焦点状态与文案一致性。

## 非目标

- 不改动后端任务模型与接口协议。
- 不在本次设计中引入新的多页面信息架构，首页仍保持单任务工作台入口。
- 不新增完整的审计报告导出系统，仅为后续扩展预留结果区结构。

## 当前现状摘要

当前前端位于 `frontend/`，核心页面为 `frontend/app/page.tsx`，实际主要交互集中在 `frontend/components/thread/index.tsx` 与 `frontend/providers/Stream.tsx`。

现有方案已经具备以下能力：

- 通过输入框提交审阅请求
- 上传文件或粘贴链接
- 展示 AI 返回内容
- 通过轮询方式展示任务进度

但当前界面存在明显问题：

- 页面本质仍是“通用聊天页 + 文件上传输入框”，产品气质偏弱
- 上传、链接、输入、状态、结果都被压缩在同一个消息流中
- 长结果内容缺少结构化阅读层次
- 工具调用与进度信息混杂在主阅读路径中
- 空状态、处理中、失败、重试等关键状态表达不够强
- 文案与元信息仍残留旧产品语义，削弱用户信任

## 设计结论

推荐将当前首页升级为 **审计工作台**，而不是继续强化聊天界面。

相较于“优化聊天 UI”，工作台方案更适合审计场景，原因如下：

- 审计场景需要同时看到证据、输入意图、系统状态与结果
- 用户更关注可追踪性与结果可读性，而非对话氛围
- 后续若新增报告生成、证据对照、问题复核，工作台结构更容易承载

## 备选方案与取舍

### 方案 A：审计工作台

推荐方案。

特征：

- 左侧输入与证据
- 中间主结果阅读区
- 右侧状态与追踪区
- 顶部统一承载任务身份与系统状态

优点：

- 专业感最强
- 长内容阅读效率最高
- 证据与状态可持续可见
- 最适合后续扩展

代价：

- 需要改造现有单流式聊天布局

### 方案 B：左右分栏，保留聊天主轴

特征：

- 左侧输入
- 右侧聊天与结果

优点：

- 改造成本更低
- 更接近现有实现

缺点：

- 仍然保留较强聊天产品感
- 结果区与追踪区难以拉开层次

### 方案 C：仅提升视觉，不动结构

不推荐。

优点：

- 开发成本最低

缺点：

- 无法解决核心问题
- 只是把旧结构做得更好看，不能建立“专业审计工具”的认知

## 页面结构设计

### 顶部栏

用途：

- 明确当前任务身份
- 显示系统状态
- 提供新建审阅入口

建议内容：

- 产品名称：`审计底稿审阅`
- 当前会话名或当前任务描述
- 系统状态，如“系统正常”“处理中”
- `新建审阅` 按钮

设计原则：

- 顶部栏不承载复杂功能
- 重点是建立上下文，而不是堆操作按钮

### 左侧栏

分为两个区块。

#### 输入面板

内容：

- 文件上传入口
- 文件链接输入
- 审阅指令输入框
- `开始分析` 按钮

目标：

- 将所有“发起任务”的行为固定在统一区域
- 不再把输入行为埋在消息流底部

#### 证据列表

内容：

- 当前会话已上传文件
- 文件类型标签
- 文件删除入口
- 预留重命名显示名或查看详情能力

目标：

- 让用户始终知道系统当前基于哪些材料进行分析
- 增强“证据已挂载”的确定性

### 中间主区

分为两个层级。

#### 摘要卡片区

建议展示：

- 风险等级
- 异常项数量
- 证据覆盖率
- 最近更新时间或处理完成时间

目标：

- 让用户在不阅读长文的情况下先抓住结论轮廓

#### 分析结果主阅读区

替代当前“单纯聊天气泡”的主承载方式。

建议按以下分段组织：

- 结论摘要
- 关键问题
- 证据不足
- 建议动作

设计原则：

- 结果内容更像结构化审阅输出，而不是普通 AI 回复
- 保持 Markdown 能力，但外层阅读框架要更稳定

### 右侧辅助区

分为两个区块。

#### 进度状态

建议展示：

- 当前阶段
- 已耗时
- 完成百分比或阶段状态
- 最近一次状态更新时间

目标：

- 用明确阶段替代模糊 loading
- 让用户知道系统“正在做什么”

#### 调用追踪

建议展示：

- 工具名称
- 参数摘要
- 时间戳
- 成功或失败状态

目标：

- 把过程透明化
- 但不打断主结果阅读

## 关键状态设计

### 空状态

空状态应弱化“聊天启动”的感觉，强化“开始一次审阅任务”的感觉。

建议包含：

- 一句明确价值描述
- 支持上传文件与粘贴链接的双入口
- 对支持文件类型与分析结果范围的简短说明

### 上传中

需要有清晰反馈：

- 单文件上传中
- 失败提示与重试
- 已上传文件实时进入证据列表

### 分析中

当前仅靠文案轮询提示不够。

建议表现：

- 主区显示骨架屏与处理中提示
- 右侧状态区显示阶段进展，如“正在抽取表格”“正在校验证据”
- 输入区保留可见，但主操作进入受控状态，避免重复提交

### 完成态

完成后页面不应只是“出现一段回复”，而应切换为审阅结果阅读模式：

- 摘要卡片更新
- 主阅读区展示结构化结论
- 右侧显示完整追踪与耗时

### 失败态

失败信息应包含问题与下一步动作。

建议：

- 明确提示失败原因或错误摘要
- 提供 `重试`、`修改输入后重试` 两种路径
- 保留证据列表与输入内容，避免用户重复操作

### 超时态

当任务超时，不应只消失或静默失败。

建议：

- 明确显示超时
- 告知用户可以继续等待、重新发起，或缩小输入范围

## 组件改造建议

### 页面层

- `frontend/app/page.tsx`
  - 从简单挂载 `Thread`，升级为工作台页面容器
  - 保留 `Suspense`，但将 fallback 文案改为规范形式 `Loading…`

### 工作台主组件

- 当前 `frontend/components/thread/index.tsx`
  - 建议拆分为更明确的工作台结构组件，而不是继续膨胀

建议拆分为：

- `WorkbenchShell`
- `WorkbenchHeader`
- `ReviewIntakePanel`
- `EvidenceListPanel`
- `ResultSummaryCards`
- `AnalysisResultPanel`
- `ProgressStatusPanel`
- `ToolTracePanel`

目标：

- 每个组件只负责一类信息
- 降低单文件复杂度
- 让后续状态扩展更可控

### 数据与状态层

当前 `StreamProvider` 可以保留，但展示模型需要重构。

建议：

- `StreamProvider` 继续负责任务提交、轮询、错误状态
- UI 层不再直接把所有状态都映射成消息列表
- 增加中间视图模型，将任务状态整理为：
  - `idle`
  - `uploading`
  - `running`
  - `completed`
  - `failed`
  - `timeout`

同时整理出以下派生数据：

- `summaryMetrics`
- `analysisSections`
- `evidenceItems`
- `progressSteps`
- `toolTraces`

这样可以避免 UI 继续被“消息数组”绑死。

### 与现有上传逻辑的关系

`use-file-upload.tsx` 逻辑可以继续复用，但展示方式应改变：

- 当前上传项更多是消息附属物
- 改造后上传项应成为证据列表的一等信息

建议：

- 选择文件后立刻进入证据列表
- 上传成功后展示已挂载状态
- 上传失败保留条目并允许重试

### 结果内容模型

当前 AI 返回值仍可先按文本处理，但展示层应开始向结构化结果靠拢。

短期：

- 保留 Markdown 渲染
- 在主区将内容包裹为“审阅结论阅读区”

中期：

- 如果后端能提供更结构化字段，再把摘要、问题、建议拆成独立区块

## Web Interface Guidelines 修复项

以下问题应纳入本次改造范围：

- `frontend/app/page.tsx`
  - `Loading...` 改为 `Loading…`

- `frontend/app/layout.tsx`
  - 更新页面标题与描述，使其匹配审计工作台定位

- `frontend/components/thread/index.tsx`
  - URL 输入框补充 `<label>` 或 `aria-label`
  - 文本输入框补充 `<label>` 或 `aria-label`
  - 去除无替代的 `outline-none` / `focus:outline-none`
  - 占位文案中的 `...` 改为 `…`
  - 自定义按钮统一接入共享按钮样式与可见焦点态

- `frontend/providers/Stream.tsx`
  - 处理中提示中的 `...` 改为 `…`

## 文案方向

整体语气应从“通用 AI 助手”转向“专业审阅工具”。

建议：

- 更少口语化聊天提示
- 更强调任务、证据、结论、复核动作
- 错误提示必须包含下一步建议，而不只是“发生错误”

## 响应式策略

桌面端优先采用三栏工作台。

中等宽度：

- 右侧状态区下沉到主区下方

移动端：

- 改为纵向堆叠
- 默认优先展示输入区与结果区
- 证据与追踪收纳为折叠区

本次设计的首要优化对象仍是桌面端，因为当前产品明显以审计工作场景为主。

## 迁移策略

建议分阶段实施。

### 阶段 1：结构调整

- 完成页面工作台框架
- 拆出头部、输入区、证据区、结果区、状态区

### 阶段 2：状态增强

- 统一空状态、上传中、分析中、失败、超时、完成态

### 阶段 3：内容升级

- 优化结果区层次
- 提升追踪区扫描效率
- 完成文案与可访问性修复

## 验证方式

设计完成后的实现验证应至少覆盖：

- 上传文件、删除文件、重复上传提示
- 粘贴链接与输入指令联合提交
- 任务运行中的状态切换
- 成功结果的结构化展示
- 失败、超时、重试路径
- 键盘焦点可见性
- 表单标签与可访问性属性完整性

## 最终结论

本次优化不应停留在“把聊天页面做得更漂亮”，而应把首页升级为一个真正的审计工作台。

核心判断如下：

- 当前产品最缺的是信息架构，而不是单点视觉修饰
- 工作台方案能显著增强可信度、可读性与可扩展性
- 在保留现有前端与状态逻辑基础上，可以通过组件重组完成这次升级

因此，后续实施应围绕 **工作台结构化改造** 展开，而不是继续沿用单一消息流作为页面主骨架。
